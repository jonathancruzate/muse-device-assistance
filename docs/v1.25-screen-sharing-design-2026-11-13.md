# v1.25 — Screen sharing: streaming view + takeover (design, 2026-11-13)

Jonathan's order (2026-11-13 19:59 EST, side chat): "Add screen sharing
streaming to device Assistance app so you can see the screen and take
it over as needed."

## What already exists (audit, same night)

- Transport: the app is relay-only since the v1.9 cut. Its stored base
  is the box device relay (`100.85.53.70:8792`, tailnet), and commands
  arrive as allowlisted `{template, args[]}` over
  `GET /phone-bridge/commands`, one per 60 s BridgeService cycle,
  gated on-device by `ShellAllowlist`, executed by `ShellBridge`,
  results posted back. The relay is a JSON-only node:http server with a
  4 MB body cap and a JSON-only response shim (it stringifies every
  response) — raw binary cannot ride it as-is.
- Hands: `VoiceAccessibilityService` is already granted and running.
  It inspects windows, taps nodes, and fires global actions. It does
  NOT yet dispatch gestures (tap at coordinates / swipe) and its
  config does not declare screenshot capability.
- Eyes: none. `screen_foreground` reports only the foreground
  package/activity — never pixels.
- Gates pattern: optional modules ship OFF behind Jonathan's in-app
  switch (voice module is the template); while off, the Worker verb is
  refused — the capability does not exist. TV profile gates phone
  surfaces off. Every router (Buds / Wear / Files / SelfUpdate) is a
  native template family with a dedicated `ShellAllowlist` validator
  and typed values that never become shell text.

## Design

### Two ways to see, because Android has two doors

1. **Snapshot (`screen_shot`) — AccessibilityService.takeScreenshot**
   (API 30+; the S24+ runs API 35). No per-session consent: the
   accessibility grant Jonathan already gave is the gate (the config
   gains `canTakeScreenshot`). One frame per command, JPEG-uploaded to
   the relay. This is Muse's "peek" — works any time the module is
   enabled, even with the screen on the launcher, no dialog.
2. **Stream (`screen_start`/`screen_stop`) — MediaProjection.**
   True continuous view needs MediaProjection, and Android requires
   the system's consent dialog **every session** — no owner-app
   exemption exists; any design claiming silent projection start is
   lying about the platform. So:
   - From `MainActivity` ("Start screen sharing") the consent dialog
     launches directly.
   - From a remote `screen_start` command, the app posts a tappable
     "Start screen sharing" notification (and tries a direct activity
     launch first — background-activity-launch rules usually block it,
     the notification is the reliable path). One tap from Jonathan
     starts the stream. The command result says exactly that
     (`consent_required`) instead of pretending.
   - The stream runs in `ScreenCaptureService`, a foreground service
     of type `mediaProjection` (Android 14+ requirement), with a
     persistent notification carrying a Stop action.
   - Capture: `VirtualDisplay` + `ImageReader` at reduced resolution
     (long edge ≤ 720 px, aspect preserved), ~4 fps, JPEG q55,
     frames POSTed to the relay as base64-in-JSON (fits the relay's
     existing JSON plumbing and caps: ~60–150 KB/frame).
   - Auto-stop after 10 minutes (a forgotten stream is a battery and
     privacy cost); Jonathan or Muse can stop it sooner
     (`screen_stop`, the notification, or the app UI).

### Takeover = the accessibility service's hands

All input is executed by `VoiceAccessibilityService` through
`dispatchGesture` + global actions + node actions — never shell
`input` (the loopback lane stays what it is; gestures need the
service anyway for node finds). Coordinates on the wire are
**normalized 0–1000** on both axes (the visual-grounding convention),
scaled to real pixels on-device from the active display metrics, so
Muse never needs the phone's resolution.

- `screen_tap <x> <y>` — one tap.
- `screen_swipe <x1> <y1> <x2> <y2> <ms 50..2000>` — one stroke.
- `screen_key <back|home|recents|notifications|quick_settings|lock>`
  — `performGlobalAction`.
- `screen_text <words…>` — `ACTION_SET_TEXT` on the focused editable
  node (dedicated free-text validator, voice_bridge pattern).
- `screen_find_tap <label words…>` — exact text/content-description
  match in the active window, tap the node or its clickable parent.
  Coordinates are the fallback; named controls are the reliable path.

Standalone (not streaming), these ride the normal command channel —
up to one bridge cycle of latency, fine for deliberate steps.
**While streaming**, the capture service also polls the relay's fast
input queue (~350 ms) so the live viewer feels interactive; the same
validators bound what the queue can carry (relay-side type/range
checks mirror the on-device ones; the device re-validates every
input before dispatch).

### Relay additions (additive; existing routes untouched)

- `POST /screen/frame` — app uploads `{frame_b64, w, h, ts,
  streaming}`; relay decodes to `store/screen_latest.jpg` + a
  `screen:meta` record (seq, bytes, at, w/h, streaming).
- `GET /screen/frame.jpg` — latest JPEG (raw response; the plumbing
  gains a raw-response path alongside the JSON shim).
- `GET /screen/meta` — meta + pending-input count + app state.
- `POST /screen/state` — app posts stream state (started/stopped,
  frame count, last error).
- `POST /screen/input` — Muse queues one validated input event.
- `GET /screen/input` — the app drains the queue (returns + clears).
- `GET /screen/view` — a self-contained viewer page: live image
  (poll-refresh), click-to-tap, Back/Home/Recents buttons, a text
  box, and stream state. Auth is the same relay secret on every
  route, as everywhere else.

### Gates and safety (house rules, applied)

- **Module switch**: `Store.K_SCREEN_ENABLED`, default OFF, flipped
  only by Jonathan in `MainActivity` (voice-module pattern). Every
  `screen_*` verb except `screen_status` refuses while off.
  `screen_status` always answers (enabled / accessibility /
  streaming / last frame / last error).
- TV profile: all screen ops refuse.
- Frames go only to the app's configured base (his relay) with the
  on-device secret; the secret is never logged; frames are never
  written to the phone's storage.
- Every report's `shell_bridge` gains a `screen` object (state only).
- Streaming is visibly indicated on-device the whole time (the FGS
  notification + the system's projection indicator) — Android
  enforces this; the design leans into it.

### Muse side

- `phone-bridge-cmd.sh enqueue screen_* …` works unchanged for the
  command lane.
- New `tools/screen.sh`: `shot` (enqueue + wait + download latest
  frame to `screen-out/latest.jpg`), `start|stop|status`, `tap`,
  `swipe`, `key`, `text`, `find` (fast input queue when streaming,
  command lane otherwise), `fetch` (latest frame only), `view`
  (prints the viewer URL). Frame download tries the VM tailnet
  forwarder first, then `ssh cat` of the box store file.
