# v1.36.0: files subfolder navigation + image fetch (2026-11-24)

**Version:** 1.36.0 (versionCode 51), up from 1.35.0 (code 50).
**Trigger:** Jonathan, 2026-11-24: "Upgrade device Assistance to be
able to do this", after the ABG audit's phone pass hit the two
v1.24 limits head-on: `files_list` saw direct children only (the
bulk of phone media sits in app subfolders: Pictures/Instagram,
DCIM/Camera, Movies/DFinstagram), and no template could return a
file's content, so phone-local media could not be visually
screened at all.

## What shipped in the app

- **`files_list` subfolder navigation (extended, same template).**
  New shape: `files_list <folder> :: <segment...> [offset]`. The
  `::` marker is what switches shapes, so the v1.24 contract
  survives exactly: without it, `files_list <folder> [offset]`
  behaves byte-for-byte as before and a non-numeric second arg is
  still a bad offset, never a surprise subfolder. Each segment is
  ONE argv element (quote it when it contains spaces, e.g.
  `files_list dcim :: "Clipped images"`), validated by
  `FilePlan.segmentOk` (the direct-child name rules: no
  separators, no parent references, no dotfiles, no control
  characters), depth capped at `FilePlan.MAX_SUB_DEPTH` = 4.
  Inside the `::` section a trailing numeric arg is the offset
  only when at least one segment precedes it, so a numeric-only
  subfolder works bare (`files_list dcim :: 2024`) and with an
  explicit offset (`files_list dcim :: 2024 0`). Output format is
  unchanged (page of 40, newest first, `F|D / size / mtime /
  name`); the header gains `sub=<a/b/c>` and the `more:` line
  echoes the full `::` command shape. On-device, `FileRouter`
  re-resolves the chain and canonical-checks containment inside
  the mapped base folder, so a symlink planted in a public folder
  cannot walk a listing (or a fetch) outside it.
- **`files_get` (new native template).** Shape:
  `files_get <folder> [segment... ::] <name...>`; without `::`,
  every arg after the folder is the file name (word args joined,
  the joinName pattern) and the file sits in the folder root.
  Images only (jpg / jpeg / png / webp / gif, gated on extension
  in `ShellAllowlist.checkFiles`, re-checked in the router, and
  magic-byte-verified at the relay). Hard cap
  `FilePlan.FETCH_MAX_BYTES` = 2,500,000 bytes of the ORIGINAL
  file: above it the router refuses typed `files_too_large`.
  Nothing is downscaled or truncated, ever, so the SHA-256 the
  command reports is the original file's hash and the receiver
  verifies the delivered bytes against it. Typed errors:
  `not_an_image`, `not_a_file`, `files_too_large`, `empty_file`,
  `read_failed`, `bad_subfolder_path`, `files_upload_failed`,
  plus the standing `files_access_not_granted`.
- **`FileFetchTransport.java` (new).** The fetch rides the
  existing command/relay architecture exactly the way screen
  frames do: the router reads the file, hashes it, and POSTs
  base64-in-JSON to `{base}/files/fetch` on the app's configured
  relay base (Store base + secret, never hardcoded), with
  folder / sub / name / ext / size / sha256 / ts. The command
  result then carries the stored reference:
  `files_get folder=... sub=... size=... sha256=... ref=files/fetch.bin name=...`.

## Relay side (box device-relay, deployed in this handling)

`relay/server.js` gains three routes, mirroring the screen-frame
handlers: `POST /files/fetch` (decodes the payload, refuses over
2,500,000 bytes, recomputes the SHA-256 and refuses a mismatch,
magic-byte-checks the claimed image type, stores the binary at
`store/files_fetch_latest.<ext>` plus a `files:fetch` meta
record; one fetch slot, a new fetch replaces the old),
`GET /files/fetch.bin` (raw bytes with the image content type),
and `GET /files/fetch-meta`. Deployed to the box with backup
`server.js.bak-20261124-pre-v136-filesfetch`; `device-relay.service`
restarted and verified active; `GET /files/fetch-meta` answered
`{"error":"no fetch yet"}` before the first fetch, as designed.
The same handling also folded the v1.35 `routine_fire` report
passthrough (which existed only in the box copy) back into the
project `relay/server.js`, so the project copy is again the
canonical superset. The retired Cloudflare Worker lane was NOT
updated: the phone has been relay-only since the v1.9 cut.

## Usage

```
phone-bridge-cmd.sh enqueue files_list pictures :: Instagram
phone-bridge-cmd.sh enqueue files_list dcim :: Camera 40
phone-bridge-cmd.sh enqueue files_get pictures statsfm-share-1773774140659.png
phone-bridge-cmd.sh enqueue files_get pictures Instagram :: IMG_20260419_135321_778.jpg
# then pull the delivered file from the box:
scp muse@167.233.41.12:~/device-relay/store/files_fetch_latest.<ext> .
sha256sum <file>   # must equal the sha256 in the files_get result
```
