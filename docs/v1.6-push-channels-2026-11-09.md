## What shipped in the app

- **Store keys** for all 9 channels in design §4 (`push_notifications`,
  `push_calendar`, `push_contacts`, `push_messages`, `push_dialer`,
  `push_call_log`, `push_health`, `push_battery` — all default OFF;
  `push_mode_reconcile` default ON), plus per-channel
  cursor / last-push / last-error keys, the battery latch key, and the
  PushClient retry-queue key.
- **`PushChannels`** — one registry table (id, label, wire source,
  Store keys, default) shared by MainActivity, PushClient, and the
  report snapshot, so the three surfaces cannot disagree.
- **MainActivity** — new section "Push channels — this device → Muse
  (you control each one)": one CheckBox per channel following the
  voiceCheck/shellCheck pattern exactly (`syncingPushCheck` guard,
  Store.put, BridgeLog "PUSH" line, refresh), a per-channel status
  view (on/off, last push, last error, queued retries), and the
  permission flow on turning a channel ON: cursor jumps to now (no
  historical dump); Notifications reports the already-granted
  notification-access status only; Calendar / Contacts / Messages /
  Dialer / Call Log fire their runtime-permission requests (codes
  71–75, permissions declared in the manifest); Health Connect is
  stubbed with a toast + log line (its grants live in the HC app).
  On TV every checkbox is disabled and every channel reports OFF.
- **`PushClient`** — POST `{base}/device-push?secret=…` JSON
  `{source, ts, items[]}` using the SAME base + secret as
  WorkerClient. Blocking `push()` for background threads +
  `pushAsync()` for listener/UI callbacks. Cursor / last-push advance
  ONLY on HTTP 2xx; failures set the channel's last_error and are
  logged via BridgeLog. **Retry choice (documented): an in-prefs
  queue** — failed payloads are appended verbatim to
  `Store.K_PUSH_QUEUE` (cap 200, oldest dropped) and retried by
  `flushQueue()` on each BridgeService cycle; payloads for a channel
  Jonathan has since turned OFF are dropped, never pushed behind his
  toggle.
- **Notifications channel (LIVE)** — `GroundTruthListener` keeps its
  existing Routines ground-truth parsing path first and unchanged;
  a new `forwardPush()` then forwards EVERY package's posted AND
  removed notifications via PushClient, source `phone-notify`, items
  `{package, title, text, big_text, posted_at, event, key}` — but
  only when `push_notifications` is ON. When OFF the listener's
  behavior is exactly the pre-v1.6 behavior (forwardPush returns
  before any read/log). Removed/CLEARED events are new: Notify Push
  v2 never shipped them. **Currently OFF** — it starts pushing the
  moment Jonathan flips the toggle in the app; MacroDroid Notify Push
  should be disabled by him on-phone at that point (drain dedupes in
  the meantime, per the design).
- **Low Battery channel (LIVE)** — `BatteryPush.check()` on the
  BridgeService 60-s cycle: when `push_battery` is ON, the 20%
  downward crossing latches and pushes ONE event, source
  `phone-battery`, with MacroDroid's status-POST fields (`battery`,
  `charging`, `wifi_ssid`, `ringer_mode`, `screen_on`); the latch
  re-arms above 25%. **Currently OFF** (Jonathan's toggle).
- **Report** — `WorkerClient.postReport` now carries a
  `push_channels` object: per channel `{on, last_push_at, last_error}`.
- **Manifest** — the six runtime permissions for the stub channels,
  declared (not granted), requested only from their toggles.

## Worker deploy — /device-push home: mode-sync (chosen)

**Choice: the mode-sync Worker**, not phone-ingress. Why: PushClient's
contract (design §3 + task) is "same base + secret as WorkerClient" —
the app already holds exactly one base URL + secret on-device, for
mode-sync. Putting /device-push in phone-ingress would have required a
second base/secret in the app and a new on-device setup step for
Jonathan; in mode-sync it needs none. The phone-ingress Worker keeps
owning the MacroDroid-shaped `phone-notify` text/plain intake during
the overlap.

Changes to `~/workspace/cloudflare-workers/mode-sync/worker.js`
(backup `worker.js.bak-20261109-pre-v16-device-push`):
- `POST /mode-sync/device-push` — auth via the existing modeAuthed
  (poll/phone-push secrets); source allowlist (the 8 push sources);
  items sanitized field-by-field (typed caps for phone-notify and
  phone-battery; generic capped shape for the v1.7 sources), stamped
  `received_at`, appended to KV `devicepush:<source>` (queue cap 500,
  ≤50 items per post).
- `GET /mode-sync/device-push?source=…` — authed read-back of a
  source's queue (the drain contract for the follow-up drain step).
- Report sanitizer: `push_channels` passthrough (known channel ids
  only; `{on, last_push_at, last_error}` capped) — without this the
  new report field would have been dropped server-side, as
  shell_bridge's voice fields once were.
- Deployed with the preserve-bindings lane (`deploy.py`): HTTP 200,
  success true, all pre-existing bindings preserved (MODE_SYNC KV,
  POLL_SECRET, PHONE_PUSH_SECRET, PANEL_SLUG).

## Deviations / notes

1. **Worker home vs the app's endpoint naming** — none in the app:
   PushClient posts to `{base}/device-push` on the mode-sync base
   exactly as designed; the mode-sync choice (above) is what makes
   that true with zero on-device setup. **No on-device step is owed
   by Jonathan for the endpoint.**
2. **BridgeService restart needed a shell start** (above) — a
   consequence of the update killing the sticky service on this
   Samsung build, not of v1.6 code (onCreate is unchanged in shape;
   the v1.4.2 guarded startForeground path held: no crash records).
3. **deviceidle whitelist grep artifact** — an early
   `dumpsys deviceidle whitelist | grep metamuse` printed "not
   whitelisted", but the report's `tailscale.battery_exempt:true` and
   StatusProducer's `battery_unrestricted` read the PowerManager state
   directly; the grep was a dump-format artifact, not a lost grant.
   (Not independently re-verified via cmd deviceidle in this run.)
4. **Drains are not in this slice** — /device-push queues items; the
   VM drain consumers (design step 4) are the follow-up. Until then,
   with both live channels OFF, nothing is queued in production
   except the one marked deploy-test battery item.
5. github-export snapshot synced in this handling (sources, build.sh,
   manifest, SKILL.md, this record, README build record); git push
   not run, per the established pattern for this project.
