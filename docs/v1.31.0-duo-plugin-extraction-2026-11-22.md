## What changed: the Duo feature set left the core

At Jonathan's order (2026-11-21), every Surface Duo-specific feature of Device Assistance moved out of the core APK into a separate plugin app, **Muse Duo Companion** (`com.jonathancruzate.metamuseduo`, project `~/workspace/muse-duo-companion/`), following the Galaxy Buds plugin precedent. The core keeps only generic host duties.

### Moved to the plugin

- The wake ritual: `ACTION_USER_PRESENT` evaluation, posture gating (hinge angle, `DuoPosture`), the 2-minute debounce and in-flight latch, fire bookkeeping (fires, last_fire_at, last_result).
- Duo debug mode: the flag, its set-at timestamp, and the suppression counter.
- The `duo` command namespace execution: `duo_debug_on`, `duo_debug_off`, `duo_debug_get`, and read-only `duo_panels_get`.
- The Duo snapshot that feeds the relay report's `duo` object.
- The Duo settings/status UI (ritual switch, wake-pair toggle and mode, debug toggle, status block), as the plugin's own MainActivity.
- The wake pair (new in this run, owned by the plugin; windowing executed by DuoPanel 0.2.1): on open + unlock at the home screen, Muse pinned left and the DuoPanel picker pinned right. See the plugin DESIGN.md and DuoPanel PATCH-0.2.1.md.

`DuoRitual.java` and `DuoPosture.java` are deleted from the core (dex string count 0). The old `duo_panels_on` shell template is deleted from `ShellAllowlist` entirely: the v1.26-era ritual's `ensurePanelsProp` SET `persist.debug.phh.duo.panels=true` on every evaluation. That behavior does NOT carry forward. The plugin reads the prop read-only via `getprop` and never writes it; the prop was verified `false` repeatedly through this run, including via `duo_panels_get`.

### Kept in the core (generic host duties)

- **DuoRouter** (modeled on BudsRouter): routes allowlisted `duo_*` templates to the plugin over explicit components with a nonce-matched reply PendingIntent (`DuoResultReceiver`). A missing plugin returns a typed plugin-missing result.
- **PluginVoiceService**: a signature-permission-guarded generic endpoint a plugin uses to request a voice activation (payload plus a no-PiP-return flag). `VoiceBridge` gained the generic plugin-requested path; the Duo ritual payload constant moved to the plugin.
- **Snapshot passthrough**: WorkerClient includes the plugin's duo snapshot in the report unchanged.
- **Plugins section in MainActivity** (new UI): lists each registered plugin (Galaxy Buds, Duo Companion) with installed state and version, an **Open** action that launches the plugin's settings/status activity by explicit intent, and an **Uninstall** action firing the system uninstall flow for the plugin package. Plugin apps carry NO launcher activity and never appear in the app drawer (Jonathan's order, 2026-11-22, Galaxy Wearable model). The old Duo section is gone from the core UI.
- Minimal `DeviceProfile` Duo detection plus the duo-bridge wire identity and phone-surface gating the relay depends on.

IPC in both directions is signature-permission guarded (same family cert); no open endpoint.

### REQUEST_DELETE_PACKAGES fix

The Plugins section's Uninstall initially self-closed without showing a prompt: the core lacked the `REQUEST_DELETE_PACKAGES` permission, so the uninstall activity finished immediately. The permission was added to the core manifest, the core rebuilt and reinstalled, and the flow retested: the system uninstall prompt for Muse Duo Companion appeared, was cancelled, and the plugin was confirmed still installed and healthy.

### Pre-existing gap found (not a regression, not fixed in this run)

After an in-place DA upgrade, BridgeService does not restart on its own: MainActivity only starts it when the service flag is off, and an upgrade leaves the flag on with the process dead. Recovery is one tap on the in-app Start bridge control (used twice in this run). Worth a small fix in a later build: on MainActivity create, if the flag is on but the service is not running, start it.

## Defects found late in the run, and their fixes

1. **Plugin snapshot staleness.** A relay report mixed live fields with migration-era fields (fires, debug, wake-pair mode from an old snapshot). Root cause: DuoStore writes used `SharedPreferences.apply()`, which is lost when the plugin process dies before the async write flushes. Fix: DuoStore writes use `commit()` (class doc explains why). Verified by cold read after process death: state durable.
2. **Debug mode cleared on service start + 60-minute TTL (the urgent 2026-11-22 03:21 EST bug).** The plugin initially copied v1.29 semantics: `DuoService` cleared the debug flag on start and the flag hard-expired after 60 minutes, so a verified `duo_debug_on` read back off within minutes (set_at wiped to 0) while Jonathan was watching TV, and the ritual kept greeting the TV. Fix, shipped in the installed plugin build (SHA-256 `7fe17a2a08821920ed0dfab3442271d524ea63c720c459501704a3bde78f3b94`): clear-on-start deleted entirely (service call and `DuoEngine.clearDebugOnStart` removed); the flag persists until explicitly turned off via `duo_debug_off` or the in-app toggle; a 12-hour backstop remains and `duo_debug_get` reports `expires_at`; `duo_debug_on`'s result text says it persists until `duo_debug_off`. The remote flag and the in-app toggle behave identically.
3. **Wake-pair result delivery lost under voice-session churn.** The activity-result chain through two trampolines timed out silently (25 s) three times. Redesigned to the BudsRouter shape: the plugin mints a mutable reply PendingIntent per attempt, a nonce-checked `DuoPairResultReceiver` takes the outcome, `DuoCommandActivity` forwards the PendingIntent and finishes immediately, and DuoPanel's WakePairActivity sends the PendingIntent (setResult kept as secondary). Pair timeout reduced to 12 s. DuoPanel's launch-log write also switched to `commit()` (same apply-loss class as defect 1).
