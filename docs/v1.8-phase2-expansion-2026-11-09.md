## What v1.8 changes

### Actuation — night-only → all house modes (`Actuation.java`, rewritten)

v1.3's gate fired only for desired=night and refused outright
when the Away latch was running. v1.8 keeps every v1.3 gate and
widens the mode scope:

- Fires only when ALL hold: the in-app ARM switch is ON (default
  OFF; Jonathan's act) · desired ∈ {home, away, night, morning} ·
  verdict is `drift` on a fresh, parse-verified dump · the step
  has not already been fired for this desired `seq` · the step's
  routine is linked in-app. Disarmed = shadow-observe only,
  exactly as before.
- **Sequenced multi-step plans, one fire per cycle, each step
  verified against a fresh dump before the next fires:**
  - desired=away, latch not running → fire the linked Switch
    Away routine once per seq.
  - Non-away target with the Away latch running → the latch is
    toggled OFF as its own once-per-seq fire (`clear_away` step,
    markers `act_away_clear_seq/at/gt`); the target fires only
    once a later fresh dump shows the latch gone. If a fresh
    dump still shows the latch after its toggle, the sequence
    records **blocked** — the target is never fired over a held
    latch and the toggle is never machine-gunned.
  - Mode already at target but Away latched → the clear is the
    only step.
  - **Drifted-latch clear stays un-automated**: a mode that
    reads active while its switch routine is not running needs
    an ON-then-OFF toggle pair (two blind toggles); the decision
    is recorded as blocked with that reason, as in v1.3.
- **Fire outcomes** resolve from ground truth, not from the fire
  call: `verified` (verdict reaches in_sync, or the Away latch
  is gone on a fresh dump), `not_engaged` (a fresh dump still
  shows the drift the fire was meant to end), `superseded` (a
  newer desired seq arrived first). Stored on the last-fire
  record; BridgeLog carries each transition.

### Shadow evidence — every report now carries `actuation`

Computed EVERY cycle, armed or not (parity proof must not need
arming), stored in prefs as JSON (`act_shadow_json`,
`act_last_fire_json`, `act_history_json`) and attached by
`WorkerClient.postReport`:

```json
"actuation": {
  "armed": false,
  "linked": {"home": "<routine name or ''>", "away": "", "night": "", "morning": ""},
  "shadow":  {"at", "seq", "desired", "observed", "verdict", "armed",
              "action": "none|would_fire|fired|awaiting_verify|blocked",
              "step": "fire_target|clear_away|clear_drifted_latch|",
              "target", "routine", "reason"},
  "last_fire": {"seq", "desired", "step", "target", "routine",
                "at", "gt_at", "outcome": "pending|verified|not_engaged|superseded",
                "outcome_at"},
  "history": [ …≤12 decision-change entries {at, seq, desired, action, step, target} ]
}
```

Per mode change, this is the diff surface for goal_2b6213617252:
the local loop's would-fire/did-fire decision and its verified
outcome, alongside the report's observed ground truth — directly
comparable against what MacroDroid Mode Poll / mode-sync actually
did with the same desired change.

## Verification caveat — Cloudflare KV daily write cap (account-level)

The fresh-report read-back could NOT complete in this handling,
for a platform reason proven three ways:

1. The stored report stayed at received_at
   **2026-11-09T15:10:58Z** through every read after the install,
   and the device-push notify queue's tail stopped at 15:18Z —
   both predate the Worker deploy (~15:26Z) and the install
   (15:27:55Z).
2. Direct probes: report POST (with and without an `actuation`
   object) and device-push POST all return **HTTP 500 (error
   1101)** — every KV-writing handler throws — while all GETs
   (report, mode-state, device-push) answer normally. The
   deployed code passes the same requests locally (above), so
   the fault is not in the code.
3. A direct KV write through the Cloudflare API returned
   **HTTP 429, error 10048: "your account has reached the free
   usage limit for this operation for today."** The MODE_SYNC
   namespace (and the account's KV writes generally) hit the
   free-tier daily write cap on 2026-11-09 — the day's v1.6/v1.7
   deploys plus the live notification-push volume. (A KV DELETE
   still succeeds; deletes are not the capped operation.)

Consequences, all time-boxed: KV writes recover at the daily
reset (**00:00 UTC 2026-11-10 = 19:00 EST 2026-11-09**). The app
keeps cycling; PushClient queues failed pushes in prefs and
retries each cycle, and the bridge posts reports on change /
15-min heartbeat — so the first post-reset report will carry
verdict + `push_channels` + the new `actuation` object with no
action from anyone. Expected final state in that report:
verdict in_sync (Home, seq 174), `shell_bridge` unchanged,
`push_channels` all ON **except Health OFF** (see below), and
`actuation.shadow.action = "none"` (verdict in_sync) with
`history` holding the decisions since install.

**Follow-up owed:** one read of `phonebridge:report` after
00:00 UTC 2026-11-10 to confirm the `actuation` object landed
and the invariants above held; if the shadow record shows
anything unexpected, it will be visible there directly.
