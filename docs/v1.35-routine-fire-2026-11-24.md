# v1.35.0: command-driven routine firing (MacroDroid retirement build, 2026-11-24)

**Version:** 1.35.0 (versionCode 50), up from 1.34.0 (code 49) in tree; the phone went 1.33.0 (code 48) to 1.35.0 in one self_update step.
**Goal:** give Device Assistance a generic Samsung Routine firing module that can replace the MacroDroid universal macro, without repeating the v1.23 mistake.

## What shipped in the app

- **`RoutineFirer.java` (new, recovered and generalized).** The pre-v1.23 firer was recovered verbatim from GitHub (`jonathancruzate/muse-phone-bridge` @ `8cd7445d23cd9af75c47c6eb43911b43986ea80c`, v1.3.x, old package name) and generalized from 4 house modes to a fixed 16-key registry. Capture-based firing, exactly as proven before: linking runs Samsung's own CREATE_SHORTCUT picker (`com.samsung.android.app.routines/.ui.shortcut.ShortcutCreationActivity`), stores the minted shortcut intent URI plus its display name in on-device prefs (`rf_link_<key>` / `rf_link_name_<key>`), and firing replays that intent. The app never hand-builds a routine intent.
- **Registry keys:** sleep, home, away, morning, theater, driving, exercise, work, relax, before_bed, commute_home, commute_work, meeting, power_standard, power_max, status_full.
- **Command-driven only (the critical difference from pre-v1.23).** There is NO Actuation engine, NO desired-poll firing, NO reconciler hook, and NO arm switch. `BridgeService` and `Reconciler` are untouched. A routine fires only when an explicit relay command arrives: new native template **`routine_fire <key>`** in `ShellAllowlist.NATIVE_TEMPLATES`, gated by `checkNative` against a fixed key pattern, executed by `NativeCommands` into `RoutineFirer.execute`. Typed errors: `not_linked`, `bal_blocked`, `routine_app_missing`, `fire_failed`, `profile_gated`, `unknown_key`. Every attempt (success or failure) is recorded to `rf_last_key` / `rf_last_at` / `rf_last_result`.
- **`sound_set <sound|vibrate|mute>` (new native template).** AudioManager ringer mode with read-back verification; replaces routine-control's `?do=sound` branch in the prepared DA leg. Without Notification Policy Access, transitions into or out of silent refuse typed as `policy_access_not_granted`. DND was NOT duplicated: the existing `dnd_on` / `dnd_off` DA templates remain the DND path.
- **MainActivity link section (phone profile only).** One "Link routine: <label> (<key>)" button per registry key (request codes 80 to 95), the recovered `startActivityForResult` / `onActivityResult` flow, and a status view listing each key's linked routine name or "(not linked)" plus the last fire record. Deliberately NO test-fire button and NO arm checkbox: linking is Jonathan's tap; firing is Muse's explicit command. TV and Duo profiles render no section.
- **Report gains `routine_fire`** (phone profile only): `{linked: {<key>: <routine name or ''>}, last_fire: {key, at, result}}`, attached in `WorkerClient.postReport` beside the voicemail object.
- **Report whitelist passthroughs (the v1.21 lesson, applied in the same handling):** the mode-sync Worker (`worker.js`, backup `worker.js.bak-20261124-v135-routinefire`, deployed via `deploy.py`: HTTP 200, success true, all pre-existing bindings preserved) and the box device-relay (`~/device-relay/server.js`, backup `server.js.bak-20261124-v135-routinefire`, `device-relay.service` restarted and verified active) both sanitize and pass `routine_fire` with the 16 known keys only.

## Low Battery verdict (verified from code)

**Nothing acts on a MacroDroid "Low Battery" status POST, and nothing needs to.**

- battery-guardian.py samples the phone itself: its `sample_battery()` reads phone state through its own lanes (the ingress poll and device reads), computes drain rates and zones, and only ever WRITES by firing power modes. No code path in it, or anywhere else in the smart-home tree, consumes an inbound MacroDroid Low Battery POST.
- Device Assistance's own battery push channel was removed in v1.33.0 at Jonathan's order (docs/v1.33.0-battery-channel-removal-2026-11-23.md): in the live `app/src` tree `BatteryPush.java` is absent and `PushChannels.java` carries the REMOVED comment. The `BatteryPush.java` still visible under `github-export/app/src` is a stale pre-v1.33 export snapshot, not live source; the stale "LIVE Low Battery latch" wording at in-repo `SKILL.md:261` is leftover pre-removal text.
- Conclusion: the MacroDroid Low Battery macro can be deleted with the rest of the universal macro set whenever the retirement completes; no replacement is required.
