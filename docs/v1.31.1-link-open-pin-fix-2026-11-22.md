# v1.31.1 — link_open launch fix: resolve-then-pin (2026-11-22)

Fixes the `link_open` launch path built in v1.28.0
(`docs/v1.28-link-open-2026-11-19.md`). The v1.28 validator
(`ShellAllowlist.checkLinkOpen`: https only, meeting-host
allowlist, no userinfo, chunked args) is **unchanged** — this
version touches only the executor, `NativeCommands.openLink`.

## The failure (live, 2026-11-22, phone on v1.30.1 / code 42)

With the phone unlocked and in active use, `link_open
https://meet.google.com/` reliably failed:

- `cmd-12383262` → ok=false, ms=2700, `bal_blocked: foreground
  did not become a meeting app/browser for meet.google.com
  (stayed com.twitter.android)`
- `cmd-7718d414` → ok=false, ms=2701, same `bal_blocked`
  (stayed `com.google.android.gm`)
- `cmd-f38d0c1f` → ok=false, ms=3863, same `bal_blocked`
  (stayed `com.google.android.gm`)

Each attempt consumed the full ~2.5 s foreground-verify window;
`startActivity` never threw.

## Diagnosis (differential tests, same phone, same hour)

- `app_launch com.android.chrome` → ok, foreground Chrome
  (555–1615 ms). `app_launch com.google.android.apps.tachyon`
  (the Meet app) → ok, foreground tachyon (1075 ms). Explicit /
  package-pinned launches from the accessibility-service
  context work fine under active use — this is NOT a blanket
  background-activity-launch block.
- `app_launch com.google.android.apps.meetings` →
  `app_not_launchable` (that package has no LAUNCHER intent on
  this phone; the live Meet app is `…apps.tachyon`, already in
  link_open's expected set).
- The same unpinned `link_open` "succeeded" once
  (`cmd-b013a245`, ok, fg=tachyon, 126 ms) — but the Meet app
  was already foreground when it fired (launched 30 s earlier
  by the app_launch probe), so the verify poll saw the
  pre-existing foreground, not a launch. Not a real pass.

Root cause: the v1.28 form fired the ACTION_VIEW intent
**unpinned**. On this phone (Galaxy S24+, Android 16 / One UI)
an unpinned https VIEW issued from the background in active use
never brings a handler to the foreground (it dies in
resolution — chooser/app-link default handling — without an
exception), so the verify window always expired. The sibling
verbs that pin their target (app_launch's explicit component,
nav_open's `setPackage(Maps)`) never had this failure mode.

### The anomalous success read (cmd-12383262)

One status read of cmd-12383262 briefly showed ok /
fg=`com.google.android.apps.meetings` / 145 ms, while the
durable command record and a repeat attempt both show
bal_blocked. From the code and relay behavior available, the
explanation that fits is a double execution with result
overwrite: the command was executed once under a warm-Meet
state (fast foreground match — the same shape as the genuine
126 ms already-foreground pass above, with the meetings
package's VIEW handler foregrounding), the result post did not
settle the record, and a later re-execution under active use
posted the bal_blocked result that the record now durably
holds. This cannot be proven byte-for-byte from the surviving
records; what is certain is that the durable record plus two
further full attempts all failed, so the failure was treated
as the truth throughout this fix.

## The fix (NativeCommands.openLink)

**Resolve-then-pin.** Before launching, the executor now asks
the PackageManager who can handle the validated URL and pins
the intent to one concrete package (`Intent.setPackage`):

1. the host's native meeting app, when it actually handles
   the URL (queryIntentActivities ∩ expectedPkgsForHost,
   browsers excluded);
2. the system default handler, when it is a real app and not
   a resolver/chooser package;
3. Chrome, then Samsung Internet, when they handle it;
4. any other non-resolver handler.

Then the launch proceeds exactly as before (accessibility-
service context, NEW_TASK, foreground-verified ~2.5 s), with
the verify set widened to the expected set **plus** the pinned
target (a pinned third-party browser default is a legitimate
landing). The success string now carries the pin:
`foreground=<pkg> host=<host> via=<pinned pkg>`. No handler at
all is a new typed error, `no_handler: no installed app
resolves https://<host> …`. Typed-error honesty is unchanged:
non-arrival is still `bal_blocked`, never a false ok, and
there is still NO shell fallback.
