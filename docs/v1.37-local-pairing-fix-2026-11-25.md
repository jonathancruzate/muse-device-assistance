# v1.37.0: local pairing fix (2026-11-25)

**Version:** 1.37.0 (versionCode 52), up from 1.36.0 (code 51).
**Trigger:** the Muse Launcher Pack pairing with Device Assistance
had never worked. Verified ground truth before this fix: the phone's
fresh relay report showed `local_channel {paired:false, count:0,
refused:0}`, so no pairing claim had ever reached
`LocalChannel.call()` (every refusal path increments `refused`).
The widget app on the phone is v5.3.2, signed with the ONEMUSE cert
SHA-256 2746d2a2..., which matches this app's hardcoded
`PACK_CERT_SHA256`, so cert verification was not the bug. Two gaps
remained: opening the pairing window required an in-app tap in
Device Assistance (nothing on the relay channel could open it), and
a failed claim surfaced no reason anywhere server-side.

## What shipped in the app

- **New native template `local_pair_open`** (no args):
  `ShellAllowlist.NATIVE_TEMPLATES` entry plus its `checkNative`
  validation (no args, op `local_pair_open`), executed by
  `NativeCommands.openLocalPairing`, which calls
  `LocalChannel.openPairingWindow(ctx)` and returns ok with the
  window expiry (`pairing_window_open until=<epoch ms>`). Phone
  profile only: on TV/Duo profiles it refuses typed
  `profile_gated: local_pair_open is phone-only`, following the
  RoutineFirer profile-gate pattern. Pairing can now be driven
  end to end from the relay: enqueue `local_pair_open`, then tap
  Complete pairing in the Launcher Pack within 5 minutes.
- **`LocalChannel.openPairingWindow` now returns the expiry**
  (epoch ms); the MainActivity caller is unchanged in behavior.
- **Refusal bookkeeping:** `LocalChannel.refuse()` now also records
  the refusal reason and timestamp in Store (new keys
  `K_LC_LAST_REFUSAL` / `K_LC_LAST_REFUSAL_AT`), and
  `LocalChannel.snapshot()` is extended with `window_open`
  (bool: pending-until > now), `last_refusal` (string), and
  `last_refusal_at` (long), so pairing state and failures are
  visible in the relay report.

## Companion change (Launcher Pack v5.3.3)

`DaClient.claimPairingWithReason` returns the Device Assistance
error string (or the caught exception's simple name) instead of a
bare boolean, the setup wizard's failure toast reads
"Pairing did not complete: <reason>", and the unpaired instruction
string names Device Assistance's real pairing UI. Widget APK:

`7b803d3ad872b95fe0061e7dc6a68c1878ecfaffef73c69dd474df9c38b738ce`
